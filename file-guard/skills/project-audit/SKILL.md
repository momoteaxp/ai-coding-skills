# Project Audit（项目开发审计）

## 触发

用户说“审计 / 做一次审计 / 审计这个项目 / 代码审计 / 开发审计 / 检查项目质量 / 审一下 / 帮我审审”时，**直接开始**，不要反问“审什么”。

如果用户明确说“只审结构/只审目录”，改用 `fileguard-audit`。
如果用户明确说“深度/全面/深入/性能/成本/安全”，进入深度模式。

## 0. 解析项目

- **项目根**：从当前工作目录向上找最近的 `project_meta.json`；没有就用当前工作目录。
- **项目类型**：读 `project_meta.json` 的 `type`；没有 meta 时按目录特征判断。
- **纯数据/notes**：`type` 为 `kb`/`data`，或没有代码文件 → 只做数据/文档一致性，明确告知“不做代码审计”。
- **模式**：默认基线；用户说“深度/全面/深入/性能/成本/安全”才做深度；用户说“只做规则自检/检查规则冲突/规则审计”则只跑 `audit.py --project`，不跑代码审计，报告写 `_scratch/规则自检-YYYYMMDD.md`。

## 1. 解析标准（按优先级）

1. `<项目根>/docs/开发审计标准.md`
2. `<项目根>/docs/开发审计补充.md`（叠加；与标准冲突时以更严格者为准）
3. `<套件根>/templates/开发审计标准.md`
4. 本 skill 末尾的“最小清单”（兜底）

报告模板同理：

1. `<项目根>/docs/审计报告模板.md`
2. `<套件根>/templates/审计报告模板.md`

**套件根解析**：

1. `%COMATE_FG_HOME%`（受管根）→ `<根>\products\file-guard`
2. `%FG_HOME%`（受管根）→ `<根>\产品\file-guard`
3. 当前插件目录：`%USERPROFILE%\.comate\plugins\file-guard`（存在则用）
4. 都没有 → 只用项目本地标准；项目也没有就报告“未找到标准文件”，用内置最小清单

不要硬编码盘符或用户名。

如果标准文件都不存在，用“最小清单”继续，并在报告里写“未找到标准文件，使用内置最小清单”。

## 2. 先读规则上下文（仅受管项目）

审计前先读项目自己的规则，别凭印象：

```powershell
python <套件根>\scripts\audit_fix.py context --project <项目根> --json
```

它给出：`dirs` 白名单、`read_only_files`、`suite_owned`（套件分发件）、`root_file_name_rule`、checkpoint 读/写口径。

写发现时只用这些事实判断“这个文件能不能在项目内改”：

- 在白名单、非只读、非套件件 → **可修**；
- 只读/配置/根级文档 → **需确认**；
- 套件分发件 → **需上游**；
- C0/全局规则 → **需改规则**。

这些判断最终由 `audit_fix.py precheck` 自动复核；AI 不需要手标 A-E。

## 3. 结构/规则预检（仅受管项目）

如果项目有 `project_meta.json`，且套件可用：

```powershell
python <套件根>\scripts\audit.py --project <项目根>
```

- 把结构审计的 P0/P1 并入报告“结构/一致性”部分。
- `audit.py` 现在包含 **rule-consistency**：文档自称真源、硬编码路径、同步指纹过期、设计组件缺失、checkpoint 直接写。这些 P1/P2 直接进报告，**不需要再找套件窗口复核**。
- 不要重复代码审计已经报过的同一条问题。
- 如果 `audit.py` 不存在或执行失败，跳过，并在报告里写“结构预检未执行”。

## 3. 代码/开发审计

按标准第 3 节流程执行：

1. **定范围**：入口、核心模块、最近改动、依赖、测试；列出排除项。
2. **跑基线**：测试、构建、lint/类型检查；记录命令和结果；没有就记“缺失”。
3. **读规格**：README/文档/注释/配置，提取“应该怎样”。
4. **读实现**：按维度检查，收集候选；每条记 `file:line`。
5. **验证**：用测试/命令/输入复现；不能复现的降为“待验证”。
6. **去重分级**：同一根因合并；按 P0–P3；P2/P3 加收益/成本/风险。
7. **出报告**：用报告模板。

**默认基线维度**：正确性、逻辑与状态、一致性与矛盾、冗余与重复、安全与数据、验证与可观测性 + 开发过程卫生。

**深度追加**：效率与性能、经济性、可维护性、AI/skill 专项。

## 4. 证据规则（硬约束）

- 每条发现必须有：`file:line` + 代码片段 + 触发场景/复现 + 影响 + 最小建议 + 置信度。
- 每条建议给 `targets`（要改的文件相对路径）；**不需要手标 A-E**，工具会按规则自动判“可修/不可修”。
- 审计只给建议，不执行修改。
- 如果用户说“只列问题/不要建议”，报告只写发现和证据，不写修复建议；默认给最小建议。
- 低置信度放“待验证”，**不计入 P0/P1**。
- 没有证据的不要写；不要把“可能”写成“就是”。
- 不把风格偏好当 bug；不提议重写；不凑数。
- P0/P1 最多 20 条；P2/P3 进 backlog。
- 审计期间只读；不改代码、不改配置、不改数据。

## 5. 输出

- **报告**：`<项目根>/_scratch/开发审计报告-YYYYMMDD.md`
- **机器可读发现**：`<项目根>/_scratch/开发审计发现-YYYYMMDD.json`（字段见标准 §7.1）
- **结构/规则预检的 P0/P1/P2/P3 计入总统计与结论**；不要只算代码审计。
- **每条建议带**：targets、同步影响、验证方法。
- **聊天摘要（≤10 行）**：
  1. 结论：阻断 / 有条件通过 / 通过 / 不完整
  2. P0/P1/P2/P3 数量
  3. 可修 / 不可修（只写数量和主要原因）
  4. Top 3（P0/P1 优先）
  5. 报告路径
  6. 未覆盖项
- P0>0 时第一行必须写“阻断”，不要淡化。
- 证据不足时结论写“不完整”，不要写“通过”。
- 不自动修；修复另开任务。

## 6. 如果用户说“按报告修复”

- 先跑 `context` 读规则，再跑 `precheck`；**只修“可修”**。
- 不可修只列原因：只读/配置需确认、套件件需上游、全局规则需改 C0；不要硬改。
- 可修先产出补丁：`_scratch/fixes/fix-YYYYMMDD.patch`（用 `git diff` 生成），**不要直接改文件**。
- 预检 + 应用（套件工具，默认 dry-run）：
  ```powershell
  python <套件根>\scripts\audit_fix.py precheck --project <项目根> --findings <发现.json> --out-plan <计划.json>
  python <套件根>\scripts\audit_fix.py apply --project <项目根> --plan <计划.json> --patch <补丁> --write
  ```
- 工具会：自动判可修/不可修、`git apply --check`、备份到 `_trash/audit-fix-backup-*`、跑 verify/enforcer/audit、失败自动回滚。
- 不改 `read_only_files`、套件分发件、C0；不擅自搬目录；不自动 commit/push。
- 修后跑 `enforcer.py check` → `audit.py --project` → `doctor.py`，并对比修前结果。
- 如果最优解需要“需上游/需改规则”，停止，给出“该走哪个流程”，不要硬改。

## 7. 最小清单（兜底）

- **正确性**：空/边界/异常/编码/中文路径/保留名。
- **逻辑**：分支/状态/重试/并发/取消。
- **矛盾**：文档 vs 代码、配置 vs 默认、多处真源。
- **冗余**：死代码/重复/调试残留。
- **安全**：密钥/路径穿越/破坏性操作/权限。
- **验证**：关键路径测试/可复现/日志。
- **过程**：未提交/无关改动/版本与文档同步。
