# 项目开发审计标准

> 标准版本：v1.2 ｜ 下发方：FileGuard ｜ 更新日期：2026-10-31
> v1.2：简化处理方式——工具按 `targets` 自动判定“可修/不可修”，不再要求 AI 手标 A-E。
> v1.1：明确 checkpoint 读口径（本项目 `read_file` 可直读；规范读取优先工具；写/跨项目/扫描仍拦）；新增规则一致性审计（真源表述/硬编码/同步指纹/组件）。
> 本文件由套件下发，请勿直接修改；项目补充规则写入 `docs/开发审计补充.md`。
> 配套文件：`docs/审计报告模板.md`

---

## 0. 这份标准是什么

**是什么**：一份可执行的项目代码与开发过程审计标准。项目窗口的 AI 按它检查自己的代码，产出有证据、可复核的 P0–P3 报告。

**不是什么**：

- 不是 FileGuard 的套件结构自审计（那是 `fileguard-audit`，查目录/引用/一致性/checkpoint 契约）。
- 不是自动修复工具；审计期间只读，修复另开任务。
- 不是一次性大重构；建议必须是最小改动。

**目标**：让项目窗口能自己发现 bug、逻辑问题、冗余、重复、矛盾、效率/经济性问题和安全风险，并把“猜测”和“证据”分开。

---

## 1. 适用对象与触发时机

### 1.1 适用对象

| 项目类型 | 审计范围 |
|---|---|
| `software` / `suite` / `web` / `ops` | 9 个维度全量 + 过程卫生 |
| `skill` / `docgen` | 基线 6 维 + AI/skill 专项 + 经济性 |
| 小脚本 / 单文件工具 | 基线 6 维 |
| `kb` / 纯数据 | 不做代码审计；只做数据/文档一致性 |

### 1.2 触发时机

- 用户说“审计 / 做一次审计 / 审计这个项目 / 代码审计 / 开发审计 / 检查项目质量”。
- 新项目基线。
- 发版前。
- 重大变更后。
- 周期性（建议每月一次）。

### 1.3 两种模式

- **基线（默认）**：全项目入口 + 最近改动 + 核心模块；最多 20 条 P0/P1。
- **深度（按需）**：指定模块/性能/成本/安全；用户说“深度/全面/深入”才做，不默认全量。

---

## 2. 审计原则（硬规则）

1. **只读**：审计期间不改代码、不改配置、不改数据、不改版本号。
2. **证据**：每条发现必须有 `file:line` + 代码片段 + 触发场景/复现步骤 + 影响。没有证据不写。
3. **置信度**：高/中/低。低置信度放“待验证”，不计入 P0/P1。
4. **不猜**：不确定的标“待验证”，给出验证命令或输入；不要把“可能”写成“就是”。
5. **不凑数**：不把风格偏好当 bug；P0/P1 最多 20 条；P2/P3 进 backlog。
6. **不重写**：建议最小改动；不提议“推倒重来”。
7. **可复核**：记录跑过的测试/构建/lint/命令和结果；没跑就写“未覆盖”。
8. **独立性**：假设代码可能是错的；先读需求和文档，再读实现；主动构造反例。
9. **范围**：排除 vendor/generated/data/第三方；在报告里列出排除项。
10. **结论**：P0=阻断，P1=有条件通过，只有 P2/P3=通过；证据不足=不完整。
11. **建议不等于执行**：每条建议给 `targets`，处理方式由 `audit_fix.py` 自动判定（可修/不可修，见 §7.2）；审计不自动修；修复另开任务，并走 §7.3 的检查。
12. **不做完整补丁**：审计只给“最小修复方向”，不在报告里写完整补丁或重写方案；补丁由后续修复任务产出。

---

## 3. 审计流程（7 步）

1. **定范围**：项目类型、入口、核心模块、最近改动（`git log`/`git diff`）、依赖、测试；列出不审的内容。
2. **跑基线**：测试、构建、lint/类型检查、现有审计工具；记录命令和结果；没有就记“缺失”。
3. **读规格**：README/文档/注释/配置，提取“应该怎样”。
4. **读实现**：按维度检查，收集候选；每条记 `file:line`。
5. **验证**：用测试/命令/输入复现；不能复现的降为“待验证”。
6. **去重分级**：同一根因合并；按 P0–P3；P2/P3 加收益/成本/风险。
7. **出报告**：结论、维度状态、P0/P1 详情、P2/P3 清单、覆盖缺口、下一步；同时写机器可读的 `findings.json`（§7.1）。

## 4. 审计维度

### 4.1 正确性（必查）

**目标**：常见输入和异常下结果正确，不丢数据。

必查：

- 空/null/缺省/超长/特殊字符/Unicode/中文路径/Windows 保留名/含空格路径。
- 数值边界：0、1、-1、最大/最小、溢出、精度。
- 异常路径：抛错、超时、部分失败、资源释放、临时文件清理。
- 外部依赖：网络/文件/DB/API 失败、重试、幂等。
- 编码/时区/换行/大小写/路径分隔符。
- 并发/竞态/锁/重复执行。

证据：复现输入、测试、日志、错误码。

反模式：`except: pass`、只测 happy path、假设输入永远合法、失败后留下半成品。

### 4.2 逻辑与状态（必查）

**目标**：控制流、状态迁移、重试和失败恢复都符合预期。

必查：

- 控制流是否覆盖所有分支；提前返回/守卫是否漏。
- 状态迁移是否完整；非法状态是否有处理。
- 不变量/前置/后置条件是否成立。
- 重试/回滚/补偿是否幂等。
- 顺序依赖、初始化/销毁、生命周期。
- 并发/异步/取消/超时。

证据：状态图、时序、复现步骤。

反模式：布尔条件写反、重试覆盖已成功结果、半途失败留下脏状态。

### 4.3 一致性与矛盾（必查）

**目标**：同一事实只有一处真源；文档、配置、代码不打架。

必查：

- 文档 vs 代码；注释 vs 行为；配置 vs 默认值。
- 同一事实是否多处定义（版本号、路径、阈值、规则）。
- 命名 vs 语义；schema vs 使用。
- 两套规则是否冲突；迁移后旧入口是否还在。
- 报告/索引/README 是否与当前实现同步。
- **规则源**：文档不得自称“规则真源/唯一依据”；运行时规则以 C0 + 本项目 `project_meta.json` 为准。
- **同步指纹**：`.fileguard-sync.json` 与实物一致；本地覆盖必须登记为 `local_override`，否则 sync 会误判/覆盖。
- **组件口径**：设计文档声明的通用组件必须存在；路径模块只能有一套（`tools/_paths.py` 或 `scripts/paths.py`，不要并存）。
- **checkpoint**：本项目 `_checkpoint/latest.json` 允许 `read_file`/`grep_content`/`list_dir` 直接查看；**规范读取仍优先 `tools/checkpoint-manager.py load`**（处理旧 v2、`not_found/error`、禁用项目）。写必须走 `save`；跨项目读、扫描、`run_command` 裸读禁止。

证据：两处 `file:line` 对照；改一处另一处是否失效。

反模式：README 命令已失效、配置键没人读、两个常量不同步、注释描述的是旧行为。

### 4.4 冗余与重复（必查）

**目标**：没有死代码、重复实现和调试残留。

必查：

- 死代码、未用 import/依赖/配置/资源。
- 复制粘贴变体（行为略有差异的更危险）。
- 重叠模块/重复实现。
- 调试残留：print/console.log、TODO/FIXME、注释代码、临时文件、`.bak`。
- 过度设计：为不存在的需求预留的抽象。

证据：引用计数、grep、diff、调用图。

注意：分发副本/模板/兼容层可能是有意重复，先确认再报。

反模式：删代码只看 grep、不看外部消费者；两个实现“看起来一样”就合并。

### 4.5 效率与性能（按需；software/web 必查）

**目标**：在目标规模下不慢、不爆内存、不浪费 I/O。

必查：

- 时间/空间复杂度；嵌套循环；重复计算。
- 重复 I/O/网络/DB；N+1；批量 vs 逐条。
- 内存增长、缓存、启动时间、热路径。
- 数据量 ×10/×100 的表现。
- 并发度、锁粒度、背压。

证据：测量/基准/日志；没有测量就标“待验证”。

反模式：凭感觉说“慢”；微优化掩盖架构问题；没有规模假设就下结论。

### 4.6 经济性（按需；skill/docgen 必查）

**目标**：成本随规模可控，不为低价值功能付出高维护/运行成本。

必查：

- 运行成本：token/API 调用、云资源、计算、存储、日志增长。
- 重试/循环/长上下文/多工具调用导致的成本放大。
- 依赖重量、构建/发布/安装时间。
- 维护成本：重复维护、复杂配置、知识集中。
- 机会成本：低价值功能、过度设计。
- 是否有预算/限额/熔断/缓存/批量。

证据：调用计数、成本估算、规模假设；给“收益/成本/风险”。

反模式：只说“可以优化”，不给规模假设和成本模型。

### 4.7 可维护性（按需）

**目标**：下一个人能读懂、改对、测得了。

必查：

- 命名、函数/类长度、参数个数、嵌套深度。
- 耦合/内聚、模块边界、依赖方向。
- 错误信息是否可行动；日志是否可诊断。
- 可测试性：能否注入依赖/构造失败。
- 配置 vs 代码；魔法数；重复知识。

证据：代码片段、调用关系；不要只报“风格”。

反模式：God class、长函数、隐式全局状态、错误信息只有“失败”。

### 4.8 安全与数据（必查）

**目标**：不泄密、不丢数据、不被不可信输入操控。

必查：

- 密钥/令牌/个人信息是否进代码/日志/报告。
- 路径穿越、任意文件读写、命令注入、SQL/模板注入。
- 破坏性操作是否有确认/备份/回滚。
- 权限最小化；不可信输入；输出编码。
- 依赖漏洞/供应链；反序列化；临时文件权限。
- 数据完整性/备份/恢复。

证据：攻击输入、失败场景、配置对照。

参考：OWASP Secure Code Review Cheat Sheet；AI 项目加 OWASP Top 10 for LLM Applications。

反模式：把密钥写进示例/日志；删除操作无备份；信任模型输出直接执行。

### 4.9 验证与可观测性（必查）

**目标**：能证明它没坏；坏了能发现。

必查：

- 关键路径是否有测试；测试是否真的断言。
- 回归/夹具/可复现；测试是否依赖环境。
- 日志/指标/健康检查；失败能否被发现。
- 错误分类/告警/恢复。
- 构建/发版/回滚是否可重复。

证据：命令 + 结果；覆盖缺口要写。

反模式：只测 happy path、测试通过但没断言、日志里没有上下文。

### 4.10 AI/skill 专项（skill/docgen/AI 项目）

**目标**：触发准、指令不打架、成本可控、失败可回退。

必查：

- 触发词/description 是否准确；会不会误触发/漏触发。
- 指令是否矛盾/含糊；是否有优先级。
- token 成本：系统提示/上下文/重复注入。
- 工具调用：循环、过度代理、权限过大。
- 幻觉防护：证据要求、未知处理、输出格式。
- 提示注入/隐藏上下文泄露/不当输出处理。
- 失败回退：模型不听话/工具失败/超时。

证据：测试 prompt、调用记录、成本估算。

参考：OWASP Top 10 for LLM Applications 2026。

反模式：description 写得像广告、指令互相冲突、工具权限大于任务需要、没有预算/限额。

### 4.11 开发过程卫生（横切，所有项目）

- git 工作树：未提交/无关改动/大文件。
- 调试残留：print/TODO/注释代码/临时文件/日志。
- 版本/文档/索引是否同步。
- 破坏性变更前是否有备份/回滚。
- 测试/构建命令是否记录。
- 变更范围是否聚焦（一个任务一件事）。

## 5. 严重级 P0–P3

| 级别 | 判定 | 例子 | 处理 |
|---|---|---|---|
| **P0** | 数据丢失/安全/主流程不可用 | 覆盖写无备份、密钥入日志、主流程崩溃、破坏性操作无回滚 | 阻断，先修 |
| **P1** | 常见路径功能错/逻辑矛盾 | 条件写反、重试丢数据、严重性能退化、权限过大 | 尽快修 |
| **P2** | 冗余/可维护性/中等成本 | 重复逻辑、死代码、文档漂移、缺少非关键测试 | 排期 |
| **P3** | 风格/可选优化 | 命名、注释、微优化 | backlog |

补充：

- 同一根因只报一条，合并影响。
- P0/P1 必须能复现或给出强证据。
- P2/P3 必须写“收益/成本/风险”，否则不进清单。

---

## 6. 结论与维度状态

### 6.1 维度状态

- **红**：该维度有 P0/P1，或完全没有证据。
- **黄**：只有 P2，或存在覆盖缺口。
- **绿**：无发现且有证据（测试/测量/命令结果）。
- **不适用**：该类型不要求此维度。

### 6.2 审计结论

- **阻断**：有 P0。
- **有条件通过**：无 P0，有 P1。
- **通过**：只有 P2/P3。
- **不完整**：关键项没跑/没证据，不能下结论。

> 不允许把“没跑测试/没看核心模块”写成“通过”。

## 7. 报告要求

- 使用 `docs/审计报告模板.md`。
- 同时写 `_scratch/开发审计发现-YYYYMMDD.json`（字段见 §7.1），供 `audit_fix.py` 使用。
- 草稿写到 `_scratch/开发审计报告-YYYYMMDD.md`；定稿可放 `output/`（项目有该目录时）。
- 聊天摘要不超过 10 行：结论、P0/P1/P2/P3 数量、Top 3、报告路径、未覆盖项。
- P0>0 时第一行必须写“阻断”，不要淡化。
- 证据不足时结论写“不完整”。

### 7.1 机器可读发现（findings.json）

报告之外，同时写一份 `_scratch/开发审计发现-YYYYMMDD.json`，供 `audit_fix.py` 预检/应用。最小字段：

```json
{
  "standard_version": "1.1",
  "project": "<项目名>",
  "date": "YYYY-MM-DD",
  "findings": [
    {
      "id": "F-001",
      "severity": "P0|P1|P2|P3",
      "dimension": "correctness|logic|consistency|redundancy|performance|economy|maintainability|security|verification|ai|process",
      "title": "<一句话>",
      "file": "src/x.py",
      "line": 42,
      "targets": ["src/x.py"],
      "evidence": "<代码片段/命令输出>",
      "impact": "<触发场景/影响>",
      "recommendation": "<最小修复方向>",
      "sync_impact": "none|meta|docs|suite|all-projects",
      "verification": "<验证命令/方法>",
      "confidence": "high|medium|low",
      "status": "open"
    }
  ]
}
```

硬约束：

- `id` 唯一；`file`/`targets` 用项目内相对路径。
- `targets` 必填；工具按 targets 自动判定“可修/不可修”，**不需要手标 A-E**。
- 低置信度 findings 也要写，但 `confidence=low`，预检前人工确认。
- 这份 JSON 只写发现，不写补丁。

### 7.2 处理方式（工具自动判定）

| 处理方式 | 判定 | 谁做 |
|---|---|---|
| **项目内可修** | 目标在白名单、非只读、非套件分发件 | 项目窗口直接修 |
| **需确认** | 只读文件、配置、根级文档 | 用户确认后改 |
| **需上游** | 套件分发件（`tools/checkpoint-manager.py`、审计标准、hooks 等） | 套件窗口改，再分发 |
| **需改规则** | C0 `_rules/global-rules.json`、全局规则 | 套件窗口改 + 全量体检 |

**判定由 `audit_fix.py precheck` 完成，不是 AI 逐条标。**  AI 只需要给 `targets`。

### 7.3 修复前检查（任何修改前必做）

> 这一节是给“按报告修复”的后续任务用的；审计本身不执行。

- [ ] **先读上下文**：`python <套件根>\scripts\audit_fix.py context --project <项目根> --json`。
- [ ] **放置**：目标目录在 `project_meta.dirs` 白名单，扩展名允许，不是根目录散件。
- [ ] **只读**：目标不在 `read_only_files`；命中就先取得用户确认。
- [ ] **归属**：不是套件分发件；如果是，走 D 类上游，不要改项目副本。
- [ ] **结构**：不新增/移动目录；如需，走 `init.py --force`（merge-only）/ `new-project`，并更新 `_索引.md`。
- [ ] **规则**：不改 C0；如需，走 E 类，单独确认并跑全量 doctor。
- [ ] **一致性**：版本/文档/索引/登记表一起更新，不制造第二真源。
- [ ] **测试**：修前跑一次，修后再跑；记录命令和结果。
- [ ] **备份**：破坏性操作走 `_trash` / `trash-cli.py`，不直接删。
- [ ] **Git**：不自动 commit/push；由用户决定。
- [ ] **复检**：`enforcer.py check` → `audit.py --project` → `doctor.py`。

**可直接用的检查命令：**

```powershell
# 放置/命名/只读快查（目标文件）
python <套件根>\scripts\enforcer.py check <目标文件> --project <项目根>

# 规则上下文（审计/修复前先读）
python <套件根>\scripts\audit_fix.py context --project <项目根> --json

# 预检：自动判定可修/不可修
python <套件根>\scripts\audit_fix.py precheck --project <项目根> --findings <发现.json> --out-plan <计划.json>

# 应用：默认 dry-run；--write 才落盘（备份 + 验证 + 失败回滚）；只应用可修
python <套件根>\scripts\audit_fix.py apply --project <项目根> --plan <计划.json> [--patch <补丁>] [--write]

# 回滚：从备份目录恢复
python <套件根>\scripts\audit_fix.py rollback --project <项目根> --backup <备份目录>

# 结构/一致性复检
python <套件根>\scripts\audit.py --project <项目根>

# 运行时/部署体检（套件自身或受管项目）
python <套件根>\scripts\doctor.py
```

> `<套件根>` 用 `%COMATE_FG_HOME%\products\file-guard` 或当前插件目录解析，不要硬编码盘符。

**冲突高发场景（必须按类型处理）：**

- 给 docgen/内容项目加 `src/` → C，不是 A。
- 改 `project_meta.json` 加目录 → B，不是 A。
- 改 `tools/checkpoint-manager.py` → D，上游改；本地改会被分发覆盖。
- 手动删 `_trash` → 走 `trash-cli.py clean`，不是 A。
- 加 `.bak`/临时文件 → 违反命名规则；走 `_trash` 或版本管理。
- 改 C0 白名单 → E，影响所有项目。
- 改 `docs/开发审计标准.md` → D；项目补充写 `docs/开发审计补充.md`。

## 9. 禁止项

1. 禁止没有 `file:line` 证据的“感觉型 bug”。
2. 禁止把风格偏好写成 P0/P1。
3. 禁止建议“推倒重写”。
4. 禁止审计期间修改代码。
5. 禁止隐瞒未覆盖项。
6. 禁止同一问题换皮重复计数。
7. 禁止只看 grep 就判定“没人用”。
8. 禁止把“测试通过”当成“没有 bug”。
9. 禁止把模型/工具的输出直接当事实；要复核。
10. 禁止用“应该/可能/大概”代替证据；不确定就写“待验证”。
11. 禁止把“不可修”项硬改；只读/套件件/全局规则按原因走对应流程。
12. 禁止在审计报告里写完整补丁或“推倒重写”方案；只给最小方向。
13. 禁止改套件分发件后不回上游；本地补丁会被下一次分发覆盖。

## 11. 项目补充

项目特有规则写入 `docs/开发审计补充.md`，例如：

- 本项目的关键路径/不可退让的约束。
- 必须跑的测试/构建命令。

- 领域特定的安全要求。

补充文件与标准冲突时，以更严格者为准。
